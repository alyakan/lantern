# Lantern on your phone

A paired phone (iOS or Android, one React Native app in `mobile/`) sees the chats you have open, answers Claude's cards, sends messages, stops a turn and wakes a sleeping chat. On the same Wi-Fi, or from anywhere over Tailscale (see "From anywhere" below); a hosted relay could be added later as another transport, because pairing, authentication and encryption sit above the transport.

## Where things live

| Layer | Desktop (Rust, `src-tauri/src/remote/`) | Phone (`mobile/src/`) |
| --- | --- | --- |
| Shared state | `bus.rs` (every chat's events leave from here), `hub.rs` (what a late joiner needs: the current turn, pending prompts) | `sync/` (per-chat state rebuilt from events) |
| Protocol | `protocol.rs` (`RemoteEvent`, requests; types generated into `mobile/src/protocol/generated` by ts-rs) | `protocol/`, `view/` |
| Secure channel | `secure.rs`, `pairing.rs`, `keys.rs` (Noise `XXpsk3` to pair, `XX` to reconnect) | `noise/` (@noble, checked byte for byte against `snow` through `noise-vectors.json`) |
| Transport | `transport.rs` (WebSocket on the LAN, Bonjour `_lantern._tcp`) | `net/` (transport, discovery, connection, session) |
| Gateway | `gateway.rs` (allowlist of requests, per-phone outbox, catch-up) | `shell/` (controller), `screens/` |
| Pushes | `notifier.rs` (Expo push service; generic words, titles only if switched on) | `notifications.ts` |

The phone never sends tool input. To answer an `AskUserQuestion` it sends only the `answers`, which Rust adds to Claude's original input (`answers.rs`).

## Starting a chat, and what Claude suggests

**A chat from the phone.** `Projects` lists the folders the user has used in Claude lately and those with a chat open; `NewChat` starts a chat in one with a first message. Three layers decide, each on its own: the gateway (the folder must be exactly one of `Projects`, an absolute path with no NUL, the message written and at most 20,000 characters, at most five starts per phone per ten minutes), then the window (it checks the project and message again, because any window can emit the event it listens to). The chat starts on **Ask**, whatever Permissions the project was left on, unless the phone asks for **Auto** and the Mac lets phones use it (below); its questions come to the phone like any other. It runs on the preset (which models do what, Settings › Models) the phone chose, else the project's own. It is started beside what the window shows: the window doesn't switch to it, and neither the project's Permissions or preset nor the folder to reopen is recorded. The backend asks the window through `remote-new-chat`, waits up to 15 s for its answer (`remote_new_chat_done`), and tells the phone the slot once the hub lists the chat, so the phone can follow it.

**Ask, Auto and the models, from the phone.** Settings › Remote control has **"Let paired phones use Auto"**, off by default (`allow_phone_auto` in the saved settings). Off, a phone can't start a chat on Auto or put one there; on, it can. Turning it off doesn't change chats already on Auto. A phone asks the Mac what it may choose with `Controls` (whether Auto is allowed, and the presets the window lists), puts a chat on Ask or Auto with `SetPermissions`, and on a preset with `SetPreset`; a chat's mode and preset come in the chat list (`RemoteChat.permissions` and `.preset`). The Mac decides, in two places that each read the setting themselves and never take it from the request: the gateway (Auto only if the setting is on; a preset only if it is one the window listed, by exact id, because the window would otherwise quietly run another; the chat must be listed, awake and idle, since a switch restarts its claude and would drop what it is doing and withdraw a question it asked; a switch to what the chat already is does nothing, so a phone can't make claude restart over and over), then the window (the same, again, because any window can emit what it listens for; and never over background tasks, whose restart it would ask the user about with nobody there; a team's Lead or agent isn't switched from a phone). Lowering to Ask is always allowed. A phone's switch is not the project's choice: it doesn't become the project's Permissions or preset. The phone shows what a chat runs on as text under its title ("lantern · Auto · Max"), opens a "Chat settings" sheet (Permissions and Models) when the title bar is pressed, and has a "Runs on" row in the New chat sheet, only for a Mac whose Welcome lists `controls` in `features`: an older Mac ends the connection at a request it doesn't know, so it is never sent one. **Not yet tried with a real Lantern and a real phone:** the settings sheet, a switch restarting a real claude, and whether the half-width swipe bar fits "Swipe to approve".

**Step by step from the phone.** A phone shows Step by step's pages (Frame, Step 2 of 4, "Switch to Build"…) as cards with the Mac's own buttons, and now chooses the Workflow too: a chat is started as Chat or Step by step (`NewChat.workflow`), and a chat is put on either with `SetWorkflow`, from the chat's settings sheet or the New chat sheet. A chat's workflow comes in the chat list (`RemoteChat.workflow`: chat, steps or team). The Mac decides, in the gateway and again in the window: only while the chat is idle (the switch restarts claude), never onto Team (a team is started and led on the Mac), never a team's Lead, and a switch to what the chat already is does nothing. A phone's switch is not the project's Workflow. Only for a Mac whose Welcome lists `workflow` in `features`.

**Closing a chat from the phone.** `Close { slot }` closes a chat on the Mac as closing it in the window's sidebar does (its conversation stays in History). The gateway refuses a chat that is working or waiting on someone ("Stop it first"), then the window checks again (it also refuses a team's Lead or agent, and a chat with background tasks, whose stop the sidebar would ask the user about with nobody there). The phone offers it in the chat's settings sheet and by holding a chat down on Home, always asking first, and only for a Mac whose Welcome lists `close` in `features` (`protocol::FEATURES`): an older Mac ends the connection at a request it doesn't know.

**Commands, plan, context and plan usage ("extras").** A phone that can read them says so in its Hello (`features: ["extras"]`, `net/session.ts` `PHONE_FEATURES`), and only then does the Mac send them (`protocol::to_remote_for`, `Session.extras` in the gateway): a phone that doesn't know an event kind can't draw the chat. They are `RemoteEvent::Commands` (the slash commands and skills claude offers, capped), `Todos` (the plan Claude keeps with TodoWrite, from the new `UiEvent::Todos`, which the window is never sent), `Context { tokens, window }` (what the chat holds; `window` from a turn's result, also carried on `TurnDone.context_window`, which an older phone ignores), and `ServerMessage::Plan` (the subscription's five-hour usage: the account's, so a message of its own, sent when a phone connects and when it changes). The hub keeps the latest of each (`SessionHub::extras`, `plan`) so a phone that opens a chat is told them whatever the kept events no longer reach; they come at the end of a catch-up. The phone offers `/` in the message box (`view/slash.ts`, the desktop's `matchCommands`), a plan card over the box (gone once every step is done), the usage as a strip on Home and a row in the chat settings sheet (and in the title's line once it passes 80%), and the context in the title's line and the sheet (amber at 75%, red at 90%, as the Mac's meter). The phone's reducer ignores a pushed message kind it doesn't know.

**What a step printed.** `StepOutput { slot, tool_use_id }` answers with what a finished step printed (cut to 20,000 characters) while the hub still keeps it; an older step, or a chat restored from History, answers that it isn't kept. The phone asks when a line of a grouped chip ("Ran 5 commands") is tapped. The Mac decides what may be read, not the phone: only the output of a command (Bash), a skill, a helper (Agent/Task), the advisor and an MCP tool (`hub.rs` `output_may_be_read`), found by the step's own start in what the hub keeps. What Claude read from a file or the web (Read, Grep, Glob, WebFetch, WebSearch), what it wrote, and any tool the list doesn't know are refused, so a phone can't be used to read a `.env` Claude opened. A command can still print a secret, and Lantern has no scrubber for that; the phone is paired with Noise and already sees prompts and diffs. Only sent to a Mac whose Welcome lists `output`.

**Projects keep their order.** Home's Projects view and the New chat sheet list projects by name, not by how recently their chats moved, so they don't jump about.

**Suggestions.** When nothing waits on the user, Home shows up to three drafts ("carry on in that chat", "start a chat in that project") that Claude made from the recent chats, and a button to start something of one's own. The Mac makes them with one call to a small model (`suggest.rs`: Haiku, no tools, no MCP servers, no settings or hooks, no saved session, run from the temp folder, stopped after 60 s). It spends the user's Claude usage (a small Haiku call), so it is bounded: **the model is called at most once a minute, whoever asks and however busy the chats are**. One copy is kept for every phone until the chats change (what was last said or replied in them, or where they stand: not a streamed piece of a reply, so a busy chat doesn't count as a change) or half an hour passes; within a minute of the last call whatever is kept comes back, even if the chats moved on; one call runs at a time; a failure isn't retried at once; the phone keeps them ten minutes too; and nothing is asked while something waits on the user. A request like this one, or a chat opening, runs beside the phone's other work (at most three at once per phone), so a phone waiting on Claude can still answer a prompt and hear its chats. What the model replies is treated as hostile: parsed strictly (at most three items, every field capped, control characters removed), a chat it names must exist and a project must be named, never given as a path, and a suggestion is only ever a draft in a sheet the user reads, changes and sends themselves. The model is told chat titles, project names and the last thing said and replied in each chat, never a folder path.

**Swipe to go back.** On a phone, the top screen (a chat, or a decision) can be dragged away from a 20 pt strip at the screen's left edge (`ui/AnimatedStack.tsx`, rules in `view/back.ts`). A chat follows the finger with Home sliding out from beneath it, as it did coming in; a decision is taken off to the right. It goes back past 40% of the width, or on a flick to the right faster than 0.4 pt/ms, and springs back otherwise. The strip swallows touches in those 20 pt, as the system's own back swipe does. Tablets don't use the stack, so this isn't theirs (the chats' column has its own edge drag). **Tested with synthetic touch events only; never a real finger.**

**The order of the chats.** What needs you first, then what is working, then the rest (idle, asleep, stopped), each the newest first (`view/home.ts` `byOrder`; a tie falls to the slot, so it is always the same order). A working chat is ordered by when it *started*, not by its last event: the Mac moves a chat's `active_at` on every event, which reshuffled the list while several worked. The phone has no start time from the Mac, so it keeps the `active_at` it first saw each chat working at (`workingSince` in the sync state); a chat already working when the phone first connects counts from then. **Not seen on a device.**

**What Home remembers, and unread.** On this phone only (`prefs.ts`, the Keychain): how the chats are listed, which project cards are folded (by name, the newest 40), and where each chat stood when the phone last showed it (`seen.ts`: the Mac's `active_at` per chat, never the phone's clock; at most 60, and a chat that is no longer listed loses its mark). A chat is **unread** when it is idle and its `active_at` is past that mark: its title is bold (read ones are regular), its tile has a dot, and a folded card shows a dot and says how many in its label. Asleep, working, asking and stopped chats say so already and are never unread. The first launch ever takes what is listed as seen, so the list doesn't start out unread. An open chat keeps marking itself seen as it moves, and once more as it is left. **Not checked on a device.** The Mac moves `active_at` on every event of a chat, so a chat someone is working in on the Mac, or one woken there, shows unread on the phone until it is opened there.

**On an iPad.** The same app runs on iPad (`supportsTablet`, and `UISupportedInterfaceOrientations~ipad` lists all four orientations; the top-level `orientation` stays portrait so an iPhone never rotates, and a Pro Max in landscape would otherwise be wide enough to pass for a tablet). What layout it has comes from the window's size, not the device (`view/layout.ts`, read through `shell/useLayout.ts`), so Split View and Slide Over work. A window under 700 pt wide has the phone's layout, unchanged. At 700 pt or more, held upright or under 900 pt wide, the chat has the whole width and the chats (Home, as a 340 pt column) slide in over it from a button at the start of the chat's header, with the chat dimmed behind. They can also be dragged: from a 16 pt strip at the screen's left edge to the right to bring them in, and to the left, on the column or the dimmed chat, to send them away (`view/drawer.ts` holds the rules; the column follows the finger and settles by how far it got, or by the flick if the finger was quick; it takes the drag from a list under the finger only once it is plainly going left). **Not tried with a real finger:** the tests send the touch events, and the feel of it (the strip's width, the flick speed) is unchecked. From 900 pt wide and wider than tall, the chats stay in a column beside the chat. It is one navigation stack in all three (`shell/nav.ts`), so turning the tablet keeps the chat that is open; the chats' column is one view that is only placed differently (`shell/TabletShell.tsx`), so turning it doesn't lose where it was scrolled or which projects were folded. A chat picked in the column replaces the one shown (`jump_to_chat`) instead of stacking on it, and a decision (swipe to allow) opens over its own chat in the pane (`jump_to_review`). The chat's header, messages and message box are held to one column 860 pt wide, a bottom sheet to 640 pt, and the pairing and connecting screens to 560 pt. Panels on the right (the files a chat changed, the map) are not built yet; the pane is where they will go.

## Pairing

Settings > Remote control > turn it on > Show a pairing code. The code is a QR (and a link you can copy) holding the Mac's public key, its addresses and a one-time secret that works once, for five minutes. The phone checks the Mac's key before it sends the third handshake message.

**Pairing another device from a paired phone** (for when the Mac is out of reach). The Mac sheet on Home has "Pair another device", offered only to a Mac whose Welcome lists `pair`. It asks Face ID (or Touch ID, never the passcode) every time, then sends `PairOffer`; the Mac makes the same one-time code as its own "Show a pairing code" (`RemoteStore::start_offer`, so **a code the Mac's window is showing stops working**, since only one is open at a time) and answers with the link, when it expires, and the QR's squares (`pairing::qr_modules`) for the phone to draw with plain views (no SVG library). The second device scans it, or pastes the link under "Paste the link instead" (the copy button puts it on the clipboard, and takes it off again when the code goes if it is still there), and pairs as its own device, with its own key: the Mac lists it separately and it can be removed separately, which today is only in Lantern's Settings on the Mac. The code is held only by the sheet: it goes when its five minutes are up and as soon as the app is no longer active (the app switcher's picture is taken in `inactive`, whether or not the app lock is on), and neither side logs it. **Only the phone checks the Face ID**: the Mac can't, so a phone that is paired and unlocked can mint a device; that is no more than the same phone's terminal can do (it already runs commands on the Mac), and unpairing the phone is the kill switch for it. The second device has to reach the Mac the way any phone does: the same Wi-Fi, or Tailscale on both (the link carries the Mac's Tailscale address). **Not yet tried:** on a real iPhone and iPad (the QR scan, the paste, the Face ID prompt); the Rust side is tested through the gateway, the sheet by Jest. No way yet to see or remove paired devices from a phone.

## From anywhere (Tailscale)

Lantern runs no server for this. The Mac already listens on every address, so with Tailscale on the Mac and the phone (same account) the phone reaches the Mac's `100.x` tailnet address from any network, and everything above the transport (pairing, the Noise channel, the allowlisted requests) is the same as on Wi-Fi. What Lantern adds:

- **The Mac offers its tailnet address.** `remote/mod.rs` adds addresses in 100.64.0.0/10 on a `utun*` or `tailscale*` interface after the local ones (the interface check keeps out a carrier's or hotspot's shared address in the same range, and another VPN's). The pairing link carries them, and Settings › Remote control › Away from home shows them, or says Tailscale isn't on.
- **The Welcome carries the Mac's current addresses** (`ServerMessage::Welcome.hosts`), and the phone keeps them in place of what it saved, so a phone paired before Tailscale was on learns the tailnet address the next time it connects, and a Mac whose address changed is still found. An older Mac sends none and the phone keeps what it had. The save only happens if the kept Mac is still the one that connected (a Mac forgotten meanwhile isn't brought back).
- **The phone doesn't wait on addresses that can't answer from where it is.** Local addresses get 1.5 s (on their own network they answer in milliseconds), a tailnet address 6 s (a cold tunnel can take a few seconds), and the address that worked last goes first, so away from home it goes straight to Tailscale after the first connection. That address is also saved first (then the Mac's own list, at most eight plain addresses or names), so it survives the app being killed, and an address the Mac doesn't list (an Android emulator's `10.0.2.2`) isn't lost.
- **Keep this Mac awake** (Settings, off by default) holds an idle-sleep assertion (`caffeinate -i`, `Remote::awake`, apart from the hold that lasts while Claude works) for as long as Remote control is on. A sleeping Mac can't be reached and a phone can't wake it (wake-on-LAN doesn't cross the internet), so the phone says it may be asleep and retries. The screen may still sleep and closing the lid still sleeps the Mac.
- Pairing still needs the QR code, scanned at the Mac. **Not yet checked on a real tailnet:** whether the macOS Firewall (below) blocks a connection that arrives on Tailscale's `utun` interface the way it blocks one from the Wi-Fi, whether a Tailscale ACL is in the way, and whether iOS's App Transport Security (`NSAllowsLocalNetworking` only, in `mobile/app.json`) lets the app open `ws://100.x.x.x`, which is outside the private ranges. A phone off Wi-Fi with Tailscale on can try the first two with `http://<tailnet address>:47123` in Safari: a quick "server dropped the connection" means it reached the gateway, a spinner until it times out means something is dropping it.

## Running it

- Desktop: `LANTERN_REMOTE_FILE=/tmp/lantern-remote.json LANTERN_REMOTE_PORT=47124 npm run tauri dev` (the port is for a dev run beside the real app, which holds 47123: with the same port the dev one can't listen, and a phone paired to it talks to the real one) keeps a dev run's settings and paired phones out of the real app's `remote.json`, and its Mac key in a Keychain item of its own ("Lantern Remote control (dev)"), so nothing of the real app's is touched.
- Phone, against a scripted Mac (no Claude needed): `cargo run --example fixture_gateway -- --bonjour` in `src-tauri/`; type `pair` on its stdin for a link, open it on the phone (`xcrun simctl openurl booted "<link>"` on a simulator).
- Phone build: `cd mobile && npx expo run:ios` (or `run:android`). Expo Go can't run it: the app has native modules (Bonjour, camera).
- On a real iPhone (signed with your own team, JavaScript bundled in, no Metro): `xcodebuild -workspace mobile/ios/Lantern.xcworkspace -scheme Lantern -configuration Release -destination generic/platform=iOS DEVELOPMENT_TEAM=<team> -allowProvisioningUpdates build`, then `xcrun devicectl device install app --device <id> <the .app>`. A development-signed build stops opening after about a week.
- On an Android emulator: `npx expo prebuild --platform android` makes `mobile/android` (git ignores it), then `./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` there, built with Android Studio's own JDK (`JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`; Homebrew's JDK 17 fails in the Kotlin step), and `adb install -r app/build/outputs/apk/release/app-release.apk`. A first build takes about 15 minutes. The emulator reaches this Mac at `10.0.2.2`, so pair it with a link whose host is `10.0.2.2` (a scripted Mac's `lantern://pair?…&h=10.0.2.2&p=<port>…`, opened with `adb shell am start -a android.intent.action.VIEW -d '<link>' com.alyakan.lantern`; quote the link in single quotes and don't escape the `&`). The emulator hides its on-screen keyboard while the Mac's keyboard counts as a hardware one: `adb shell settings put secure show_ime_with_hard_keyboard 1`. Home, the chat, pairing and the keyboard lift have been seen on one; the rest of the screens, Bonjour discovery and push have not.
- The keyboard: a message box or sheet rides on the keyboard through `react-native-keyboard-controller` (`KeyboardProvider` in `App.tsx`, its avoiding view in `src/ui/keyboard.tsx` and `Sheet.tsx`), which follows the keyboard frame by frame on the native side. React Native's own `KeyboardAvoidingView` and a JS animation from the keyboard's events were both tried first and lagged behind it. The library needs Reanimated and Worklets, so a rebuild (and `pod install`) follows any change to them. The avoiding view replaces its own bottom padding, so a screen's padding goes on a view inside it.
- Pushes need an EAS project: put its id in `mobile/app.json` under `extra.eas.projectId`.
- macOS Firewall: the first time Remote control listens, macOS asks whether Lantern may accept incoming connections: Allow, or a phone connects to nothing (the connection is accepted and then ignored, so it looks like "didn't answer"). An unsigned dev build or example binary is asked about again after every rebuild; `socketfilterfw --getappblocked <binary>` says whether one is blocked. Over loopback (a simulator on the same Mac) the firewall doesn't matter, so a simulator test passes where a real phone would not.
- Clipboard: "Copy the link" puts the one-time pairing secret on the clipboard, which Universal Clipboard may sync to the user's other devices. It works once and for five minutes only.

## Tests

- Rust: `cargo test` in `src-tauri/` (the gateway, hub, bus, pairing, notifier and Noise vectors).
- Phone: `npx jest` in `mobile/`. With `LANTERN_FIXTURE_GATEWAY` set to the fixture gateway's binary, `src/integration/` also runs the phone's real code against the real Rust gateway.
- CI regenerates the protocol types and fails if `git status` shows a difference.
- Maestro flows in `mobile/.maestro/` (pair, deny, swipe to allow) are written but have never been run: Maestro isn't installed where they were written. The same steps were done by hand in the iOS simulator (see below), so expect small fixes to the first real run.

**Not yet tried for real:** the suggestions call to Claude has only run against the scripted Mac's canned reply and in tests. Whether Haiku answers with bare JSON under that system prompt, and that `ask_claude` works from the running app (the window tells the backend where `claude` is), needs one try with the desktop app and a paired phone. A chat started from the phone has likewise only been exercised against the scripted Mac and the window's tests.

## What was run by hand

On the iOS simulator, against `fixture_gateway` (the real Rust gateway behind scripted chats): pairing by deep link and the confirmation, reconnecting on launch, Home with live updates, the decision screen, deny, the swipe-to-allow drag (answer reached the Mac and Home updated), and a streaming chat. All of it over loopback. Not run: Android, a real device, the camera, push, Maestro. Simulator quirk when scripting taps with `cliclick`: the first mouse-up after a system alert is sometimes lost, which looks like a stuck button; send another `du`.

## Not built yet

- A Live Activity for a running turn.

## Releasing the phone app (TestFlight, Google Play)

Done from the Mac that has the keys, with fastlane (`mobile/fastlane/Fastfile`), the way the Prayers app is. No secret is in the repository or in a GitHub workflow; each is a file on this Mac, named by a variable (the list is at the top of the Fastfile). `fastlane check` (from `mobile/`) builds and sends nothing, and says what a release is missing.

**One-time setup, Apple.** In App Store Connect create the app with the bundle id `com.alyakan.lantern` (it is permanent), and a store name that is free (plain "Lantern" is likely taken; "Lantern for Claude Code" is the repository's own description). Create the three tips as consumable in-app purchases with the ids `com.alyakan.lantern.tip.small`, `.medium` and `.large` (Small Coffee $0.99, Large Coffee $2.99, Generous Support $9.99, as in Prayers), and the two pledges as auto-renewable subscriptions in one subscription group, "Support Lantern" (`com.alyakan.lantern.pledge.monthly`, $1.99 a month, "A small monthly thank-you"; `com.alyakan.lantern.pledge.yearly`, $19.99 a year, "A yearly thank-you, two months on the house", as in Notesy), each with a name, a description and a review screenshot of the support sheet. A subscription must show its terms where it is sold (the sheet does: it renews by itself, how to cancel, and links to the Terms of Use and the Privacy Policy), and the app's page must name a Terms of Use (Apple's standard licence agreement is fine). Fill in the privacy policy and support URLs (App Review opens them; Prayers keeps its pages on GitHub Pages, and `alyakan.github.io` has a page per app), App Privacy ("Data Not Collected": the phone talks only to your own Mac; if push notifications are switched on, say that the Expo push token is sent to Expo's service), and the age rating (4+). Then `fastlane ios beta` archives and uploads a build. Testers inside your App Store Connect team can install it as soon as it has processed; a public link needs a short beta review of the first build.

**One-time setup, Google.** In Play Console (a developer account, $25 once) create the app with the package `com.alyakan.lantern`, create the three tips as in-app products with the same ids, and the two pledges as subscriptions with the same ids, each with a monthly or yearly base plan and one offer, and make the first upload by hand (Play requires it). Make an upload keystore once with `keytool -genkeypair -v -keystore lantern-upload.keystore -alias lantern -keyalg RSA -keysize 2048 -validity 10000`, keep it and a backup outside the repository, and let Play App Signing hold the real signing key. Create a service account with release rights and keep its JSON key on this Mac. `fastlane android beta` then builds a signed bundle and uploads it to the internal testing track. A new personal developer account has to run a closed test with at least 12 testers for 14 days before it can publish to production; a beta needs nothing more.

**Tips and pledges.** Three one-time tips and two ongoing pledges, all optional and bought with StoreKit 2 and Google Play Billing through `expo-iap` (`src/platformTips.ts`); `src/tips.ts` is the logic and is tested alone. A pledge makes a "regular": the app's accent changes from cobalt to Ember (a warm orange) for links, "Expand", the send button and the working bar (`src/ui/accent.ts`, given to the whole app by `AccentFromPledge`). Everything else stays free for everyone. Whether a pledge is running is the store's word, asked at launch and after every purchase; its list of what is running can be wrong for a moment, so a regular is never made one again by a single empty answer (it is asked twice a second apart before Ember goes), and whether a pledge was running is remembered on the phone so the accent shows before the store has answered. The store needs the products to exist (Ready to Submit in App Store Connect is normally enough for TestFlight's sandbox purchases, not yet tried here; active in Play Console, installed from a testing track, with the tester's account added as a licence tester) before the sheet shows anything but "Tips aren't available right now". A preview build with `EXPO_PUBLIC_FAKE_TIPS=1` shows made-up tips and pledges that "go through" after a moment, for trying the sheet with no store; the release lanes refuse to run with it set, or with it in any `mobile/.env*` file (Expo's bundler reads those too). Nothing is locked behind a purchase and the only perk is the accent, so the phone does not verify a purchase beyond what the store reports; on Apple the native layer under `expo-iap` (OpenIAP) only reports transactions StoreKit has verified. A purchase the store never answers is given up on after three minutes (the sheet says a payment may still be counted, and the listener still finishes it if it arrives). The sheet has a Restore purchases button for a pledge bought on the same account on another phone, which Apple expects wherever a subscription is sold. What the phone remembers about tips and pledges is kept on the device only (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`, and `android.allowBackup` is off), which is what the privacy policy says.

**App lock.** Optional, off by default: the Mac's sheet has "Lock with Face ID" (Touch ID, fingerprint or face on Android; the phone's passcode always works as the alternative, so a failed Face ID never locks anyone out). Turning it on or off asks for the check first, so it is proved to work and a phone handed over for a moment can't drop it; a phone with no passcode can't turn it on (and a lock left on after the passcode is removed stays open, since it couldn't be opened). When on, the app is locked at launch and again after half a minute in the background (`GRACE_MS`; time away is only counted in the background, because the Face ID prompt itself makes the app inactive for a moment and must not re-lock it), and on iOS an inactive app is covered so the app switcher's picture shows no chat (Android has no inactive state: its recents picture is taken before the app hears it is in the background, so a chat can show there; hiding it needs `FLAG_SECURE`, which also blocks screenshots, and isn't done). It is a lock on the screen only: the connection to the Mac and the chats keep running underneath, and a notification still arrives with its text (the lock doesn't hide it; the phone's own notification settings do). The setting is read before anything is shown, and one that can't be read counts as on. The logic is `src/lock.ts` and is tested alone; `src/platformLock.ts` is `expo-local-authentication` and a flag in the Keychain (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`); `src/shell/LockGate.tsx` is a Modal over the app, and every `Sheet` draws the same cover (`LockCover`) inside itself, because a Modal can't always be shown over another (iOS presents one at a time; Android shows the newest on top), so whichever is on top covers the app. `NSFaceIDUsageDescription` comes from the plugin in `app.json`, so Face ID needs a native rebuild. **Not yet tried on a real phone:** the Face ID prompt itself, and an open sheet being covered when the app comes back after half a minute.
